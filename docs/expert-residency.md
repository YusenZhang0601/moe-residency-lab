# 专家统计与按预算分配

## 从调用记录得到画像

当前模型有 48 层，每层 512 专家，每次路由选择 top-k 10。计数单位是一个 `(layer, expert)` 被路由选中的次数。

历史 Windows 计数器通过命名管道流式聚合，将累计数组保存为固定大小 STRC v1。48×512 几何下账本为 393,268 字节，STRP v1 画像为 196,632 字节。逐 token 路由原文可以持续产生大量磁盘写入，聚合数组则受到专家数量约束。

模型身份绑定记录仓库、revision、量化及权重/pack 指纹；换模后计数从零开始，旧排名可以单独复制为启动先验。原计数器保留在 `reference/routing_counter_20261104.py`，源码指纹在 `data/provenance.json`。

## 字节热度算法

对专家 e，计算

$$
s_e = \frac{c_e+1}{b_e}
$$

其中 `c_e` 为累计路由选择次数，`b_e` 为该层单个专家 blob 的字节数。分数相同时先比较调用次数，再按稳定的层内编号排序。

给定预算，从排序开头逐个装入，遇到第一个放不下的专家后，GPU 前缀结束。后面更小的专家继续进入下一层级。这个规则保留画像前缀语义，求解的是一种贪心策略。

历史三层版本还对 RAM 补集内部按层重排，并保留边界 guard。离线工具导出纯全局密度顺序，适用于已核对的全 RAM 路径。部分 RAM/SSD 布局还需要按当时加载器语义核对边界与排列，原实现单独保留供研究。

## 三个不同的观测量

| 量 | 定义 | 用途 |
| --- | --- | --- |
| 静态历史覆盖 | 排名前缀内专家的累计选择数 / 账本全部选择数 | 预算分析 |
| 运行时 GPU 本地份额 | GPU 本地执行的路由项 / 所有路由项 | 检查实际驻留效果 |
| 请求时延 | 排队、恢复、prefill、decode、传输等阶段的观测 | 判断用户体验 |

运行时指标须核对分母。某些历史 API 的 `hits/lookups` 排除了 PCIe offloaded 项，需结合 `offloaded` 才能得到全部路由项口径。原生批量汇总与 API 首窗口统计也应分别解释。

例如，A6000 冻结累计排名对 25 GiB 的历史覆盖估计约 90.85%，特定后续动态负载的 GPU 本地覆盖超过 98%。动态晋升、统计时期和工作负载都不同，两个数字可以同时成立。

## 学习与生效的时间

外部累计统计长期保存，画像定期重写。该历史部署的 `--expert-profile` 在启动时读取。引擎内部的近期热度另外用于运行时自适应晋升。因此应记录画像 SHA、生成时间、启动加载 SHA，以及运行时统计。

旧版 `--dump-routing` 曾遗漏批量 MMQ 预填充；早期“prefill+decode 全覆盖”表述已据后续源码核对纠正。每份账本应声明覆盖起点和路径。投机验证路由也可能包含后来未输出的计算，计数总量需要和 API usage 分开记录。

## 第一版代码的用途

`python -m moe_residency` 读取 STRC v1 和显式布局文件，检查账本 SHA，比较频率与字节热度排序。用户还可以提供已有 STRP 作为基线。报告包含账本选择数与 records×top-k 的一致性观测。

没有观察到调用的专家通过 `+1` 获得确定的先验次序。全零账本的覆盖比例输出 null。预算按字节计算；原生 `--expert-cache N` 的换算仍需遵循对应引擎的最大槽位和对齐规则。

旧账本只有累计数组，近期窗口无法从中还原。后续研究可增加有界窗口统计，并在后续负载上测试适应性；一次画像更新应经过明确加载与恢复步骤。

## 尚需完成的独立验证

保持权重、预算、引擎和调度一致，用先前负载生成画像，再用后续负载比较默认画像、频率排序和字节热度排序。现有预算实验支持整套配置的取舍，这项独立对照会进一步界定学习画像的贡献。
