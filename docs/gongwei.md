# 工位案例——16 GiB 显存与 64 GiB RAM 的取舍

## 硬件与研究条件

Intel Core i7-14700F，8P+12E、28 个逻辑处理器；RTX 5060 Ti，报告的总显存 16,311 MiB；64 GiB RAM；约 2 TB NVMe；Windows 原生推理。负载测量观察到 PCIe 5.0 ×8，空闲时的降速读数应单独解释。

模型为 Qwen3.8-Flash-Next GSQ-RCO IQ3_XXS，48 层、每层 512 专家、top-k 10，共 24,576 个层内专家。相关 Strata 研究源基线为 `46c152a1310f77cd2f0ce2c7cd213962df14fe83`，后续存在本地补丁。采用的 A 构建运行时报告 0.1.53，二进制 SHA-256 为 `70861672f32056e04171b2d1672fdc9616736fcf378697308da1e3b1ce6ea6bd`。

这些标识用于重建历史条件。模型名相同而引擎提交不同的结果，应按阶段比较。

## 从三级存储到全专家 RAM

早期显存与内存同时紧张，需要把冷专家留在文件层，并为暂停会话留空间。这个布局使文件读取、RAM 晋升、GPU 晋升与会话缓存互相影响。

后来研究全专家约 39.97 GiB 常驻 RAM 的布局，允许 GPU 缓存动态选取热点专家。它减少了稳定解码中的专家文件读取压力，但 RAM 还需要承担 PLE、工作区、系统和会话快照。因此，“全专家装得下”仍须结合启动峰值与快照接纳判断。

两种单路候选的关键区别如下。

| 候选 | 专家 RAM | KV 方式 | 主要取舍 |
| --- | --- | --- | --- |
| grow / A | 全专家 RAM 原件 | 动态增长 | 冷调用整体略快，保留单人任务路径 |
| stream64 / B | RAM 补集驻留 | 64K 物理 KV，262144 逻辑窗口 | 一部分续接解码更快，同时增加 host KV 压力 |

这里的逻辑窗口与同时占用的 GPU KV 容量分别记录。16 条暂停条目也需要受到总字节预算和接纳水位约束。

## 五组近满窗样本

每臂 5 个冷调用，输入 258,967 tokens，实际输出 1,024 tokens，保留原量化和完整专家计算。结果来自 `data/gongwei-single-frontier.json`，中位数可以通过 `examples/verify_results.py` 重算。

| 指标 | grow | stream64 |
| --- | ---: | ---: |
| 冷调用总时长中位数 | 172.895 s | 175.664 s |
| 首个输出中位数 | 153.210 s | 155.337 s |
| 原生日志 decode 中位数 | 51.8 tok/s | 54.4 tok/s |

前两组沿用了已完成测量，负载前史与后三组不同，原始 `conditioning` 字段保留。该结果适合判断本组取舍，尚不足以推出所有上下文长度的排序。

用户最后选择 A，实际日常任务通常小于完整窗口。B 保留为容量与速度的备选。人工长期稳定性由使用反馈继续观察，原先拟议的 8 小时 soak 被取消。

## 缓存连续性与启动峰值

历史源码排查发现，部分截断边界会把超出实际返回范围的验证行提交进状态。下一轮消息重建后，完整 live 前缀检查失配，回退到更老检查点。已有修复把提交限制到实际输出前缀；项目保留其代码出处和历史验收范围。

另一类回退来自容量接纳。一次完整暂停快照需要 4,593 MiB，同时要求保留 3,072 MiB，现场只有 6,894 MiB 可用，接纳失败后发生冷读。这类问题需要调整容量，和前缀格式失配分别处理。

互补驻留首次启动还遇到峰值问题。目标 RAM 已锁定，但复制过程中访问的文件映射页暂时留在工作集，导致中途空间不足。候选在每个专家复制成功后调用既有文件页释放路径，随后完成 35.90 GiB 复制和校验。此改动有 Windows 与原文件页规则的适用条件。

以上边界修复与容量验收来自历史记录。本发布保留源码配方和记录出处，GPU 数值测试与完整模型执行未在发布阶段重跑。

## CPU、视觉和算子经验

- P/E 核机器的主控、专家线程与辅助进程需要分别考虑。历史配置将推理主控与辅助任务分开后观察到改善，迁移到其他 CPU 时需要按实际拓扑重新测量。
- CPU 视觉编码保留 4,096 视觉 tokens，用 RAM 和延迟换取显存余量；重复图片特征缓存可以减少再次编码。
- GU256 对 IQ2 子格式改变线程组织，保留原 16-lane 点积与归约顺序。历史记录包含实际模型格式的数值对照；它所在的最终组合同时包含其他改动，独立端到端收益尚未拆分。

## 可迁移的结论

这台机器体现了容量边界对性能的影响。专家、KV 和暂停快照需要一起计算；单项 decode 更快的布局可能增加冷调用等待；代码优化也可能通过避免状态回退或启动峰值来改善体验。

采用本案例参数前，先确认专家字节表、模型版本、RAM 余量与任务长度，再选择能区分相应机制的有限对照。
