# A6000 案例——给缓存与四路体验留下空间

## 环境与比较边界

单张 RTX A6000，报告总显存 49,140 MiB；256 GiB RAM；双 EPYC 7542，64 个逻辑 CPU、SMT 关闭；NUMA 0 为 CPU 0–31，NUMA 1 为 32–63；Windows 原生。主板条件使 GPU 在负载下运行于 PCIe 3.0 ×16。

本页主要实验使用原版 Qwen3.8-Flash-Next GSQ-RCO IQ3_XXS，文字引擎 0.1.56，构建提交 `06698c674673008395ba6e971580538d6b1ea6e0`。完整专家 RAM 原件约 39.97 GiB，PLE 约 26.8 GiB；四路、每路 262144 逻辑窗口、INT8 KV resident 32768、64 GiB/32 条暂停池、最小快照 2048 tokens、CPU 视觉 4096。控制面是当时安装版加本地补丁，不能仅凭文字引擎版本重建完整软件组合。

后续 SC117 换模属于另一个实验时期，本页预算表和调度表均来自换模之前。

## GPU 专家预算对照

每臂先建立 64K/64K/16K/16K 四份独立历史，再测四热、双热、单热、再次四热。每条请求最多 512 输出 tokens，两轮四热均实际共输出 2048 tokens。输出在思考段结束，因此首正文为 null。

共 75 次请求、55 次热续接，无传输错误；各臂固定顺序执行一次，四热有两个不同阶段样本。它们构成条件明确的探索对照。

| 专家策略 | 单热 | 四热第一轮 | 四热回切 | 最低观察空余显存 | 两轮 GPU 本地覆盖 |
| --- | ---: | ---: | ---: | ---: | --- |
| auto 动态 | 6.406 s | 17.079 s | 22.484 s | 1.498 GiB | 99.8% / 99.9% |
| 28 GiB 动态 | 7.156 s | 17.359 s | 21.407 s | 8.896 GiB | 99.0% / 99.7% |
| 25 GiB 动态 | 6.469 s | 17.156 s | 21.375 s | 11.937 GiB | 98.7% / 99.5% |
| 28 GiB 固定 | 7.219 s | 17.719 s | 22.297 s | 8.978 GiB | 92.4% / 92.8% |
| 28 GiB 每 64 窗口晋升 | 6.797 s | 17.390 s | 21.844 s | 9.017 GiB | 95.9% / 99.7% |

完整聚合测量与原生窗口行在 `data/a6000-budget-B1-summary.json`。最低显存来自目标间隔 100 ms 的采样，瞬间更低的峰值仍可能漏采。25 GiB 对应 `11522 × 2329600` 字节的参数预算，实际变长专家装入字节略低。该组选择 25 GiB 动态，为 KV、预填充及其他工作区多留约 10.44 GiB。

固定驻留减少了晋升开销，却增加 CPU 专家工作，整体没有显示优势。已有 arena 维持 RAM 原件并 copy-in 到固定 GPU 槽，淘汰时可以覆盖临时 GPU 副本。旧文件层的指针旋转开关在这个路径没有激活。

## 缓存命中之后仍然等待

长预填充会占用控制路径。冷长请求和热短请求混合时，热请求即使只增加几十个 tokens，也可能等候入槽或下一次安全让行。

在固定 4K 分块的成对 CB3 实验中，增加允许的让行次数产生以下结果。

| 指标 | 2 次预算 | 64 次预算 |
| --- | ---: | ---: |
| 辅助请求最大队列等待 | 18.219 s | 7.505 s |
| 辅助请求最大首正文 | 18.938 s | 8.159 s |
| 整组墙钟 | 96.625 s | 98.203 s |
| 两条长请求输出总数 | 7188 | 7188 |

每臂 24 请求，辅助请求关闭思考、主请求与冷请求使用 xhigh。实际发生让行后才支持归因。该组采用 4K 分块，其收益范围与生产 auto 模式分开。原始汇总在 `data/a6000-continuous-CB3-summary.json`。

后续 CB4 把入场块缩至 2K，辅助首正文从 10.526 降到 3.989 秒，但两个同输出长任务由 76.587/85.583 增至 108.715/120.947 秒，冷请求由 26.054 增至 63.574 秒。2K 候选未采用。两臂整组输出总数不同，报告保留这一差异。数据见 `data/a6000-continuous-CB4-summary.json`。

## 统计口径修复

BYIELD 会暂停一次预填充并内部恢复。恢复时的复用量包含本次请求已经读过的输入。对外 API 应保留请求开始前的缓存量，并汇总各段新读工作。

历史真引擎验证的两个样本如下。

| 输入 | 外部缓存 | 新读量 | 原生分段时间之和与 API |
| ---: | ---: | ---: | ---: |
| 64061 | 0 | 64061 | 30205.1 ms |
| 96103 | 64086 | 32017 | 17094.4 ms |

`data/a6000-accounting-proof.json` 保留每段 DONE 数值。Mac 上针对当前上游的模拟引擎回归另外记录在上游贡献说明中，二者的版本与执行环境分别呈现。

## 其他尝试与保留问题

- 原生多槽 MTP 与足够长会话的快照接纳策略有实测依据。32 个暂停条目受到字节预算约束。
- GDN 候选 Tensor Core 路径需要 124,944 B 共享内存，超过该设备可用的 101,376 B；另一个 FP32 分块候选在 T1000 样本中更慢，未采用。
- 当时 DF2 对照没有得到可部署优势，仍保留草稿接受率、工作区和长请求的研究入口。
- GPU 视觉在历史实验中更快，但数值对照存在差异，正式方案沿用 CPU 路径。
- 线程绑在 NUMA 0，并不自动证明全部专家页都在 NUMA 0。内存页归属需要单独观察。

上述辅助结果来自历史研究汇总；一期提供的机器可核验数据集中在预算、调度和统计三条主线。其他 GPU 路径没有在此次发布阶段重新执行。
